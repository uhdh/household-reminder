## 이번 서브프로젝트의 범위

**이번에 만드는 것**: 홈 화면(`/`) 셸 — 인사말 헤더 + 4개 섹션 행 리스트 + 라우팅 뼈대.

**이번에 만들지 않는 것**: 4개 섹션 각각의 실제 기능. 이식 순서는 다음과 같이 이미
합의되었다 (각 단계는 별도 spec/plan/구현 사이클을 거침):

```
홈 화면 셸(이번 건) → 청소 관리 이식 → 생필품 관리 이식 → 감정카드 이식 → 포트폴리오 이식
```

**저장소/브랜치 전략**: 로컬 `master`(Next.js 스캐폴드 + 아이콘그리드 목업)를 기준으로
계속 작업한다. `origin/main`에 이미 올라간 별도 구현(생필품 리마인더의 정적 HTML/JS)은
강제로 덮어쓰지 않는다 — 그 파일들의 데이터/로직은 "생필품 관리 이식" 서브프로젝트에서
참고 자료로만 활용하고, main과 master의 히스토리 정리는 별도로 다룬다 (이번 스펙의
범위 밖).

## 비주얼/UX 디자인

브라우저 목업으로 3가지 방향(홈킷 앱 스타일 / 위젯 스택 스타일 / 현관 메타포)을
비교했고, **홈킷 앱 스타일**로 확정했다.

- 상단: 오늘 날짜 + "우리집 👋" 인사말 헤더
- 그 아래 세로 리스트, 4개 행 = [아이콘 칩] + [섹션명] + [우측 상태 배지]
- 행 탭 → 해당 섹션 라우트로 이동 (활성 상태인 섹션만)
- 라이트/다크 테마 모두 지원 (기존 청소관리 목업과 동일 기조)
- 아이콘 그리드(청소 관리 내부 UI)와는 다른, 별도의 대시보드형 비주얼 — 홈은 "현관"
  역할이고, 각 섹션 내부는 각자의 스타일을 유지한다.

## 섹션 상태(status) 데이터 처리

이 서브프로젝트 시점에는 4개 섹션 모두 이 저장소 안에 실제 로직이 없다. 다음 계약으로
느슨하게 연결한다:

```ts
type SectionStatus =
  | { ready: false }
  | { ready: true; label: string };

type Section = {
  id: string;
  name: string;
  icon: string;       // 이모지 또는 아이콘 키
  href: string;
  getStatus: () => SectionStatus | Promise<SectionStatus>;
};
```

- 홈 화면은 섹션 설정 배열(`SECTIONS: Section[]`)을 순회하며 각 행을 렌더링한다.
- 처음에는 4개 섹션 모두 `getStatus`가 `{ ready: false }`를 반환하도록 설정 →
  "준비중" 배지 표시, 행은 탭해도 이동하지 않음(비활성 스타일).
- 이후 각 섹션이 이식되는 서브프로젝트에서, 그 섹션에 맞는 실제 `getStatus` 구현을
  작성하고 설정 배열의 해당 항목만 교체한다. 홈 화면 자체의 코드는 건드리지 않는다.
- 청소 관리: "밀린 항목 N개", 생필품 관리: "교체 필요 N개" 형태의 카운트 라벨을
  기대한다 (정확한 계산 로직은 각 섹션 서브프로젝트에서 정의).

## 테스트 방침

프로젝트에 아직 테스트 프레임워크가 없다. 이번 서브프로젝트에서 Vitest + React
Testing Library를 추가하고, 홈 페이지 컴포넌트에 대해서만 다음을 검증한다:

- 4개 섹션 행이 이름/아이콘과 함께 렌더링되는가
- `ready: true`인 섹션은 실제 링크(`href`)로 동작하는가
- `ready: false`인 섹션은 "준비중" 배지가 뜨고, 탭해도 라우트 이동이 일어나지 않는가

e2e/브라우저 테스트는 이 범위에서는 다루지 않는다(YAGNI) — 4개 섹션이 모두 이식된
이후 필요하면 별도로 추가한다.

## 비목표 (YAGNI)

- 로그인/인증 (아직 로컬 전용, 여러 사용자 구분 없음)
- 섹션 순서 커스터마이징/드래그 정렬
- 홈 화면 상태의 실시간 업데이트(polling/웹소켓) — 페이지 진입 시 1회 조회로 충분
- `origin/main`과 로컬 `master`의 git 히스토리 정리 (별도 작업)
